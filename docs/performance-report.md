# 대용량 로그 점검 결과

2026-11-17, Windows x64 / .NET Framework 4.8 / C# 7.3 Release. 합성 데이터와 독립 콘솔로 실제 `LogReader`, `TimingData`, `TimingChart` 소스를 linked compile했다. 프로덕션 소스 및 기존 Tests는 이 감사에서 수정하지 않았다. 실행 중 사용자 프로그램은 조작하지 않았다.

## 결론

**100만 행, 163.1 MiB 입력을 독립 엔진과 실제 WinForms 화면에서 검증했다. 모든 크기와 조건에서 안전하거나 쾌적하다는 보장은 아니다.** 발견한 표시문 중복 보관과 이상 구간 중복 그리기를 개선하여 로드 메모리 최고치를 약 973→583 MiB, 극단적인 이상 차트 그리기를 약 4.40→0.27초로 줄였다. 30개 키워드 계산 약 13.6초와 정렬 중 취소 지연 약 1초는 남는다. 다음 표는 독립 측정이며 전체 폼 측정은 아래 별도 결과를 참조한다.

## 개선 후 동일 조건 재측정

부모 작업에서 적용한 표시문 지연 생성과 차트 픽셀 단위 중복 그리기 축소를 적용한 소스를 `snapshot/`에 복사해 독립 빌드했다. 아래 수치는 **1,000,000행, 동일 171,000,024 bytes 입력** 비교다. 최종 앱 종합 시험은 이 표와 구분하여 추가했다.

### 최종 WinForms 종합 시험

별도 테스트 프로세스의 실제 MainForm과 메시지 루프에서 같은 100만 행을 읽고, 가상 그리드 100만 행·검색 결과 100만 행·차트 분리·시간 필터 1초 1,000행·1,000행 원문 내보내기를 검증했다. 세 키워드와 A→B 규칙 하나를 사용했다.

- 배포와 같은 x64: 로드부터 첫 조회 완료 6,648ms, 전체 일치 검색 및 차트 재계산 3,239ms.
- 프로세스 최고 working set 784,408,576 bytes(약 748 MiB), 측정 시 managed heap 520,176,848 bytes. 독립 로더 수치와 달리 두 그리드·검색 결과·차트·UI 객체를 포함한다.
- 20ms UI 타이머의 최대 처리 간격 527ms. 조작이 완전히 끊기지 않는다는 보장은 아니며, 트리/그리드 갱신·그리기 구간에서 짧은 지연이 남는다.
- 32비트 별도 시험도 동일 기능을 통과했다(로드 7,922ms). 64비트 사용을 기준으로 배포한다.
- 재현: `Tests.exe --ui-large <artifacts/performance/data-1000000 전체 경로>`. 값은 `full-ui.txt`, 화면은 상위 artifacts/large-log-view.png. 실행 파일 옆 테스트 설정만 사용하며 사용자 배포 설정은 수정하지 않는다.
- 1GiB 입력, 네트워크 드라이브, 디스크 부족, 장시간 연속 사용은 여전히 미시험이다.

| 항목 | 수정 전 | 수정 후 |
|---|---:|---:|
| 로드 및 정렬 | 4,310 ms | 3,990 ms |
| 로드 후 managed heap | 664.8 MiB | **405.4 MiB** |
| 로드 후 private bytes | 710.6 MiB | **442.5 MiB** |
| 로드까지 peak working set | 973.1 MiB | **582.5 MiB** |
| 이상 999,992구간 전체 범위 그리기 | 4,400 ms | **267 ms** |
| 정상 이벤트 전체 범위 그리기 | 57 ms | 56 ms |
| 타이밍 30개 키워드 | 14,986 ms | 13,578 ms |

보유 managed 메모리는 약 39.0%, 로드까지 peak working set은 약 40.1% 줄었다. 이상 차트 paint는 약 16.5배 빨라졌다. 측정 횟수가 1회이므로 로드·검색·타이밍의 작은 차이는 최적화 효과로 단정하지 않는다. 차트 계산 자체의 30키워드 비용은 여전히 남는다. 267 ms의 극단적 전체 범위 paint도 높은 프레임률을 보장하는 값은 아니다.

수정본의 행수·정렬·시각 제거 표시문 내용을 검증했다. 1Mi 한글 글자×8개 초장문은 71 ms에 읽혔고 표시문 길이와 첫 글자도 확인했다. 해당 이벤트 차트의 paint는 6.3 ms였다. 이는 장문 **그리드 셀의 텍스트 출력** 성능 측정은 아니다. 잘못된 UTF-8 끝 바이트 파일도 기존과 같이 전체 제외+경고 1개를 반환했다.

수정본에서는 `DisplayText` getter를 실제로 읽을 때만 부분 문자열을 생성한다. CSV의 `string_storage`는 모든 getter를 평가한 문자량 합계이며 **수정본의 동시 보유 메모리가 아니다**. 보유 메모리 비교에는 getter 검증 이전 `load_sort` 단계의 강제 GC 후 값을 사용했다.

## 시험 조건과 범위

- 물리 메모리 32,493 MiB, 실행 직전 가용 메모리 14,405~14,641 MiB. 프로세스 x64 확인. CPU 식별: Intel64 Family 6 Model 154 Stepping 3.
- 8개 프로세스/파일, UTF-8 BOM, 한글 포함, 30종 키워드와 모든 행에 공통 키워드. 행당 약 171 bytes. 시각은 결정적 순열로 섞어 전체 정렬을 수행하게 했다.
- 100,000행: 17,100,024 bytes(16.3 MiB). 1,000,000행: 171,000,024 bytes(163.1 MiB).
- 파일을 직접 생성한 직후 읽으므로 디스크 캐시가 따뜻한 조건이다. 실제 저장 장치/네트워크 I/O 속도 측정은 아니다.
- 시간은 단일 측정값으로, 환경 변화나 JIT/GC의 영향을 받는다. 반복 로드만 별도 5회 측정했다.
- 독립 엔진 측정에는 전체 폼·트리·가상 그리드 비용을 포함하지 않았다. 차트 그리기는 실제 `OnPaint`를 독립 1200×400 비트맵에 호출했다. 이후 추가한 전체 폼 검증은 위의 최종 WinForms 종합 시험으로 구분한다.
- **1 GiB 로그 파일, 수천 파일, 32-bit 프로세스, 디스크 부족, 장시간 연속 운영은 시험하지 않았다.** 현재 입력보다 큰 데이터에 대한 메모리 보장을 제공하지 않는다.

## 메모리

| 항목 | 100,000행 | 1,000,000행 |
|---|---:|---:|
| 로드 완료 후 managed heap(강제 GC 후) | 67.5 MiB | 664.8 MiB |
| 로드 완료 후 private bytes | 94.3 MiB | 710.6 MiB |
| 로드까지의 peak working set | 116.3 MiB | 973.1 MiB |
| 원문+표시문 UTF-16 문자 payload 합계 | 52.6 MiB | 526.4 MiB |

**수정 전에는** `LogEntry.Text`와 시각을 제거한 `DisplayText`가 별도 문자열이라 원문과 본문 모두 메모리를 사용한다. 문자열 payload 값은 문자 수×2만 계산하며 객체 헤더·리스트·참조·임시 파싱 객체는 포함하지 않는다. CSV의 `peak_working_set_bytes`는 해당 단계 단독 최대치가 아닌 **프로세스 시작부터 누적 최고치**다. 일반 단계의 managed 값에는 아직 GC되지 않은 임시 객체가 포함될 수 있다.

별도 프로세스에서 100만 행을 5회 로드하고 각 결과의 참조를 해제한 뒤 강제 GC했다. 매회 managed heap은 1,142,424 bytes로 복귀했다. private bytes는 29,949,952~29,970,432 bytes였다. 해당 로더 경로에서 반복 실행에 따른 유지 객체 증가는 관찰되지 않았다. 전체 UI의 장시간 누수 시험은 아니다.

MainForm은 읽는 동안 기존 로그를 보존하므로 실제 재로드에서는 기존 데이터와 새로운 데이터가 동시에 존재할 수 있다. 이번 독립 로드의 최고치만으로 실제 앱의 최대 메모리를 추정하면 과소평가될 수 있다. 입력 1 GiB 수준의 처리 가능 여부는 별도 시험 없이는 단정할 수 없다.

## 취소 및 비정상 입력

| 항목 | 100,000행 | 1,000,000행 |
|---|---:|---:|
| 로드 취소 요청 후 반환 | 4.6 ms | 4.1 ms |
| 일반 검색 취소 요청 후 반환 | 0.1 ms | 0.2 ms |
| 타이밍 계산 취소 요청 후 반환 | 0.1 ms | 16.5 ms |
| 초장문 로드 취소 요청 후 반환 | 10.7 ms | 5.9 ms |

취소 지연은 타이머가 **실제로 Cancel을 요청한 시점부터** OperationCanceledException까지이며, 타이머 예약 지연은 제외한다. 요청 시점은 일반 로드 50 ms 후, 나머지는 10 ms 후다. 조기 로드 취소는 읽기 중의 결과이고, 마지막 전체 정렬 구간은 아래 별도 시험으로 구분했다.

별도 `sortcancel` 시험에서는 마지막 파일이 실제 열렸다 닫히는 것을 독립 스레드에서 관찰하고 닫힘 20 ms 뒤 취소했다. 100만 행에서 취소 요청 후 반환까지 **1,023 ms**가 걸렸다. 이 시점에는 파일 읽기가 끝난 뒤이며, 소스에서 최종 전체 정렬이 token을 중간 확인하지 않는 사실과 일치한다. 관찰 방식의 작은 스케줄링 오차가 있으므로 정렬 내부 정확한 명령 위치를 추적한 프로파일은 아니다. 읽기 중 빠른 취소가 전체 처리의 최악 취소 지연을 보장하지 않음을 보여준다.

행당 한글 1,048,576자짜리 8행(약 24 MiB)의 실제 파일은 정상 로드되었다(약 103~110 ms). 같은 파일 끝에 잘못된 UTF-8 바이트를 추가하면 행이 부분 반영되지 않고 해당 파일 전체가 제외되며 경고 1개가 반환되었다(약 130~148 ms). 자동 인코딩에서 UTF-8 BOM이 있는 파일이므로 fallback 시도에서도 BOM을 존중한 엄격 디코딩이 적용됐다. 무한 길이 행에 대한 자원 제한 검증은 아니다.

## 확인된 병목과 남은 사항

1. **차트 이상 구간/마커의 픽셀 중복 그리기 축소.** 100만 이상 이벤트의 단일 paint 4.40초가 직접 근거다. 정상 이벤트는 이미 같은 x 픽셀 중복을 줄이지만 이상 마커는 매번 그리고, 이상 구간도 모두 FillRectangle/DrawLine한다. 이 항목은 부모 작업에서 원본 구간 데이터를 보존하는 픽셀 단위 렌더링 변경으로 적용했고, 개선 후 표에서 효과를 확인했다.
2. **키워드가 많은 대용량 조회의 계산 비용.** 행×키워드 반복 검색으로 3개 1.49초 → 30개 14.99초가 관찰되었다. 필터·검색 변경 시 같은 타이밍 결과까지 재계산하는 MainForm 흐름이 사용자 대기 시간에 더해질 수 있다. 캐시 등 구조 변경은 무조건 추가하기보다 실제 사용 시나리오에 맞춰 별도 검토한다.
3. **취소 확인이 없는 긴 구간은 남는다.** 최종 `Entries.Sort`, 간격 중앙값/이상 목록 정렬에는 작업 도중 token 확인이 없고, `TimingData.Build` 최초 시각 범위 순회에도 없다. 마지막 파일 닫힘 후 취소 시험에서 1.02초 지연도 관찰되었다. 중간 token 확인을 추가한다면 정렬 비교 예외가 InvalidOperationException으로 감싸질 수 있으므로 사용자 취소로 일관되게 처리되는지 별도로 검증해야 한다.
4. **대용량 메모리 상한 부재.** 표시문을 지연 생성하도록 개선한 뒤에도 현재 전체 원문 데이터를 메모리에 보유한다. 측정 범위는 성공했지만 RAM이 작거나 재로드가 겹치는 환경에서는 OutOfMemoryException 가능성이 남는다. 문자열 저장 구조의 변경은 영향 범위가 있으므로 이 감사에서는 수정하지 않았다.

## 재현

프로젝트 루트 PowerShell에서 실행:

```powershell
& 'C:/Program Files/Microsoft Visual Studio/2022/Enterprise/MSBuild/Current/Bin/MSBuild.exe' './artifacts/performance/LargeLogAudit.csproj' /t:Build /p:Configuration=Release /v:minimal /nologo
& './artifacts/performance/bin/LargeLogAudit.exe' './artifacts/performance' 100000 rerun
& './artifacts/performance/bin/LargeLogAudit.exe' './artifacts/performance' 1000000 rerun
& './artifacts/performance/bin/LargeLogAudit.exe' './artifacts/performance' 1000000 rerun-retention retention
& './artifacts/performance/bin/LargeLogAudit.exe' './artifacts/performance' 1000000 rerun-optimized
& './artifacts/performance/bin/LargeLogAudit.exe' './artifacts/performance' 1000000 rerun-sortcancel sortcancel
```

현재 csproj는 `snapshot/`의 수정본 소스를 참조한다. baseline을 재현하려면 baseline-source-hashes.json과 일치하는 소스를 별도로 확보해야 한다. 최신 작업 트리 시험은 LogData.cs, IniFile.cs, TimingChart.cs를 snapshot/에 복사하고 새 결과 label을 사용한다. 기존 baseline label을 재사용하면 CSV가 덮어써지므로 주의한다.

가용 물리 메모리가 3 GiB 미만이면 harness는 시험을 거부한다. 대규모 실행은 수분 이내 외부 timeout을 두고 운영 프로그램과 분리해서 수행한다. 합성 입력은 `data-100000`, `data-1000000` 아래에 생성되며, 동일 경로의 합성 파일은 재실행 시 덮어쓴다. 다른 사용자 로그 경로를 인자로 지정하지 않는다. `edges` 임시 파일은 검사 종료 후 삭제한다.

- `baseline-100000.csv`, `baseline-1000000.csv`: 단계별 원시 측정.
- `retention-1000000.csv`: 100만 행 5회 로드·참조 해제 측정.
- `baseline-source-hashes.json`: baseline 소스 SHA-256.
- `optimized-1000000.csv`, `optimized-source-hashes.json`, `snapshot/`: 메모리/차트 개선 직후 고정 소스와 측정.
- `sortcancel-1000000.csv`: 최종 파일 닫힘 후 취소 지연 측정.
- `Program.cs`, `LargeLogAudit.csproj`: 재현용 독립 harness.
